## Quick Chat Code Execution — Production Deployment

### The Problem

Your code_executor.py uses `docker.from_env()` which connects to the Docker daemon via `/var/run/docker.sock`. Each of your 8 Citra Service containers needs to spawn **sibling** sandbox containers on the host. This is **Docker Socket Mounting** (not Docker-in-Docker).

### Architecture

```
Linux VM (Box 1 or Box 2)
├── Docker Daemon (/var/run/docker.sock)
│
├── citra-ai-prod-1 (port 7111)  ──┐
├── citra-ai-prod-2 (port 7112)  ──┤
├── ...                            ├──▶ All mount docker.sock
├── citra-ai-prod-8 (port 7118)  ──┘    All spawn sandbox containers as siblings
│
├── quick-chat-sandbox (spawned on demand, destroyed after 60s)
├── quick-chat-sandbox (spawned on demand, destroyed after 60s)
└── ...
```

### Step-by-Step Deployment

#### Step 1 — Build & Push the Sandbox Image (CI/CD or manually)

On your build machine (or in GitHub Actions), build and push the sandbox image to your registry:

```bash
# From Citra-Service repo root
docker build -t ghcr.io/trustedwear-tech/citra-ai/quick-chat-sandbox:latest \
  -f Dockerfile.quick-chat-sandbox .

docker push ghcr.io/trustedwear-tech/citra-ai/quick-chat-sandbox:latest
```

#### Step 2 — Pull the Sandbox Image on Both VMs

SSH into each production box and pull:

```bash
# On Box 1
docker pull ghcr.io/trustedwear-tech/citra-ai/quick-chat-sandbox:latest
docker tag ghcr.io/trustedwear-tech/citra-ai/quick-chat-sandbox:latest quick-chat-sandbox:latest

# On Box 2 — same
docker pull ghcr.io/trustedwear-tech/citra-ai/quick-chat-sandbox:latest
docker tag ghcr.io/trustedwear-tech/citra-ai/quick-chat-sandbox:latest quick-chat-sandbox:latest
```

The tag to `quick-chat-sandbox:latest` is important because code_executor.py defaults to `SANDBOX_IMAGE = os.getenv("QUICK_CHAT_SANDBOX_IMAGE", "quick-chat-sandbox")`.

#### Step 3 — Mount Docker Socket into Citra Service Containers

Add the Docker socket volume mount to the docker-compose service definitions. In docker-compose.yml, add to the common anchor:

```yaml
x-common: &common
  image: ghcr.io/trustedwear-tech/citra-ai/citra-service:${IMAGE_TAG}
  restart: unless-stopped
  stop_grace_period: 40s
  volumes:
    - ~/logs/Citra-Service:/app/logs
    - /var/run/docker.sock:/var/run/docker.sock   # <-- ADD THIS
  networks:
    - citra-ai-network
```

This lets `docker.from_env()` inside each container talk to the **host's** Docker daemon and spawn sandbox containers as **sibling** containers (not nested).

#### Step 4 — Set the Sandbox Image Name in Env (Optional)

If you want to use a fully qualified registry name instead of the local tag, add to .env.prod:

```env
QUICK_CHAT_SANDBOX_IMAGE=quick-chat-sandbox
```

Or if using registry directly (skip the `docker tag` step):
```env
QUICK_CHAT_SANDBOX_IMAGE=ghcr.io/trustedwear-tech/citra-ai/quick-chat-sandbox:latest
```

#### Step 5 — Create Temp Directory with Proper Permissions

The code executor creates temp directories on the **host** filesystem (via the socket mount). Ensure tmp has sufficient space:

```bash
# On both boxes — verify /tmp has space (sandbox writes go here)
df -h /tmp

# Optionally create a dedicated temp dir if /tmp is small
sudo mkdir -p /var/tmp/citra-sandbox
sudo chmod 1777 /var/tmp/citra-sandbox
```

If you use a custom temp dir, set it in .env.prod:
```env
TMPDIR=/var/tmp/citra-sandbox
```

#### Step 6 — Deploy with Existing Script

Run your normal deploy flow:

```bash
cd ~/deploy    # or wherever deploy/ lives on the VM
bash deploy.sh
# Select: prod
# Input new image tag: <your-new-tag>
```

The rolling deploy restarts each container one by one. Since the Docker socket mount is in the `x-common` anchor, all 8 prod instances get it automatically.

#### Step 7 — Verify on Each Box

```bash
# Check the socket is mounted
docker exec citra-ai-prod-1 ls -la /var/run/docker.sock

# Check sandbox image is available
docker exec citra-ai-prod-1 python -c "import docker; c=docker.from_env(); print(c.images.get('quick-chat-sandbox').tags)"

# Check a test container can spawn
docker exec citra-ai-prod-1 python -c "
import docker
c = docker.from_env()
r = c.containers.run('quick-chat-sandbox', command='python -c \"print(123)\"', remove=True, network_mode='none')
print(r)
"
```

### Security Considerations

| Layer | Protection |
|---|---|
| **Socket access** | Only Citra containers mount the socket; sandbox containers do NOT |
| **Network** | `network_mode="none"` — sandbox has zero network access |
| **Resources** | `mem_limit=512m`, `cpu_count=1`, `pids_limit=100`, 60s timeout |
| **Filesystem** | Input mounted `ro`, script mounted `ro`, only `/workspace/output` is writable |
| **User** | Non-root `sandbox` user inside the container |
| **Script validation** | `BLOCKED_PATTERNS` rejects subprocess, eval, socket, etc. before container runs |

### Concurrency Note

With 8 instances per box and each sandbox running up to 60 seconds, you could theoretically have **8 concurrent sandbox containers** per VM (one per Citra instance). Since Gunicorn runs with `-w 1`, each Citra container handles one request at a time, so at most 1 sandbox per Citra instance.

Worst case: **16 sandbox containers** (8 per box x 2 boxes) running simultaneously. Each uses 512MB RAM + 1 CPU, so budget **~8GB RAM + 8 CPU cores** per box for sandbox overhead on top of the Citra containers themselves.

### Quick Reference — Commands per Box

```bash
# One-time setup (both boxes)
docker pull ghcr.io/trustedwear-tech/citra-ai/quick-chat-sandbox:latest
docker tag ghcr.io/trustedwear-tech/citra-ai/quick-chat-sandbox:latest quick-chat-sandbox:latest

# Deploy (adds socket mount + restarts)
cd ~/deploy
bash deploy.sh    # prod → new tag

# Verify
docker exec citra-ai-prod-1 python -c "import docker; docker.from_env().ping()"
```
